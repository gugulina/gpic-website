# 商品状态与首页精选说明

> 一句话：**商品有三个展示状态（在售 / 售罄 / 下架），「售罄」是仍然看得见但买不到，
> 「下架」是前台彻底看不见；首页显示哪几件、按什么顺序，由「首页商品精选」单独决定，
> 没被选中的商品不会出现在首页。**

---

## 一、三个状态分别是什么意思

| 状态 | 存的值 | 一句话解释 | 典型场景 |
|---|---|---|---|
| **在售** | `on_sale` | 正常卖，正常展示 | 默认状态，新品上架 |
| **售罄** | `sold_out` | 东西还在页面上，但暂时没货 | 展会现场卖完了、补货周期中 |
| **下架** | `off_shelf` | 前台完全看不到，数据还在库里 | 停产、不再贩售、季节性下架 |

三者**不是**库存数字，而是管理员手动切换的「展示口径」。不需要盘点，点一下即可。

### 为什么不直接删掉

「删除」是物理删除，商品记录、图片引用、首页位置会一起消失，且不可撤销。
「下架」保留全部数据，随时可以切回在售，历史公告里提到的商品也不会变成死链。

删除只用于「这个商品录错了」这种情况。

## 二、三种状态在各环节的差异

这是本次改造的核心，逐项对照：

| 环节 | 在售 | 售罄 | 下架 |
|---|---|---|---|
| 商品页 `goods.html` 列表 | 显示 | **显示**（图片降饱和 + 售罄角标 + 「已售罄 · 补货中」） | **不显示**（后端就不返回） |
| 首页 `index.html` 商品区 | 显示（若被选入首页） | 显示，同样带售罄标记 | 不显示（即使被选入首页也会被过滤） |
| 商品页排序位置 | 排在前面 | **沉到所有在售商品之后** | 不参与排序 |
| 首页排序位置 | 按「首页商品精选」的数组顺序 | 同左 | 不参与 |
| 后台商品列表 | 可见，绿色「在售」 | 可见，橙色「售罄」 | 可见，灰色「下架」 |
| 购买导流 | 正常 | 仍可点（去平台看是否有货），但页面已明示售罄 | 无入口 |
| 静态站 `content.json` | 导出 | 导出（带 `status`） | **不导出** |
| 数据库记录 | 保留 | 保留 | 保留（只是不对外） |

### 排序规则（商品页）

```
第一关键字：状态      在售(0) → 售罄(1)
第二关键字：display_order 数字小的在前
第三关键字：名称      仅在前两者都相同时兜底，防止顺序抖动
```

在售商品之间仍然用后台「排序」字段控制先后；售罄商品不管排序值多小，都会被压到最后。
这样做的理由：访客打开商品页，第一屏应该全是能买的东西。

### 下单流程

本站**没有购物车、没有下单、也不收款**。商品页底部「线上通贩」卡片是把访客导流到
闲鱼等平台，真正的下单、库存、发货、售后都在那边完成。

因此状态对「下单」的影响只体现在**导流是否还成立**：

| 状态 | 导流处理 |
|---|---|
| 在售 | 正常展示通贩入口 |
| 售罄 | 卡片明确标注「已售罄 · 补货中」，避免访客白跑一趟；通贩入口本身是通用入口，不单独关闭 |
| 下架 | 商品卡片不存在，自然没有针对它的导流 |

> 如果某个平台链接只对应某一件商品，售罄时建议同时在后台把「通贩卡」的说明文字补一句
> 「部分商品补货中」，避免访客点进去找不到。

## 三、首页商品精选

### 规则

- 首页「周边产品」区**只渲染**「首页商品精选」里列出的商品。
- 列表本身是有序数组：**数组下标就是首页从左到右的顺序**。
- **没有被选中的商品，一定不会出现在首页**。
- 被选中但后来变成「下架」的商品，前台会自动跳过（不需要手动取消勾选）。
- 被删除的商品会自动从列表里摘掉。
- 列表为空时，首页整个「周边产品」区块隐藏（不留空框）。

### 与「排序」字段的区别

| 字段 | 管什么 | 在哪改 |
|---|---|---|
| `display_order`（排序） | 商品页内部的先后 | 后台「周边商品 → 编辑」里的「排序」 |
| `home_goods`（首页精选） | 谁上首页 + 首页里的先后 | 后台「周边商品 → 首页商品精选」 |

两者互不影响。一件商品可以商品页排第 8，但首页排第 1。

### 数据存放

存在 `site_settings` 表里，键名 `home_goods`，值形如：

```json
{ "ids": ["10000000-...-001", "10000000-...-004", "10000000-...-002"] }
```

只存 id，不冗余商品内容。改商品名、改价格不需要动这里。

## 四、后台怎么操作

进入 **后台 → 周边商品**。

### 改单个商品的状态

**方式一（快）**：商品列表每行右侧有一个下拉框，直接选「在售 / 售罄 / 下架」，
立即生效，不改动其他字段。

**方式二（细）**：点「编辑」，表单里有「展示状态」下拉，和文案一起保存。

### 设置首页展示

「首页商品精选」卡片：

- **加入首页**：把商品追加到列表末尾
- **↑ / ↓**：调整顺序
- **移除**：从首页撤下（商品本身还在，只是不上首页）

每次点击立即保存，不需要额外点「保存」按钮。

### 保存之后

后台写的是**本机数据库**。要让公网生效，仍然需要双击项目根目录的
「同步到公网.bat」，详见 `公网同步操作说明.md`。

## 五、实现要点（维护时看这里）

### 数据层

- `goods` 表新增 `status TEXT NOT NULL DEFAULT 'on_sale'`，取值只有三个。
- `site_settings` 新增一行 `home_goods`，值为 `{"ids":[...]}`。
- 迁移脚本对老库幂等：列已存在就跳过，`home_goods` 已存在就不覆盖。

### 接口层（`functions/handler.mjs`）

| 接口 | 鉴权 | 返回 |
|---|---|---|
| `action=goods` | 公开 | 过滤掉 `off_shelf`，售罄排最后，带 `status` |
| `action=all` | 公开 | 同上，另带 `homeGoods`（首页 id 数组） |
| `action=admin_goods` | **需要登录** | 全部商品（含下架）+ `homeGoods` |
| `action=save_good` | 需要登录 | 带 `status` 字段；非法值返回 `invalid_status`，不静默回落 |
| `action=set_good_status` | 需要登录 | 只改状态，不碰其他字段 |
| `action=save_home_goods` | 需要登录 | 保存 id 数组，去重但保持首次出现顺序 |
| `action=delete_good` | 需要登录 | 删除后顺手从 `home_goods` 里摘除 |

> **鉴权的坑**：`GET` 请求默认不校验 session（绝大多数是公开内容），
> 所以 `admin_goods` 单独登记在 `getAuthRequired` 里，路由层会强制要求 session。

> **状态校验的坑**：`save_good` 收到不认识的 `status` 时必须报错。
> 若静默回落成 `on_sale`，「标记下架」会变成「悄悄重新上架」，是最难查的一类事故。

### 导出层（`server/export.mjs`）

静态站没有服务端，**过滤必须在这里做完**：

- `off_shelf` 商品不写进 `content.json`（否则推上公网等于没下架）
- 每个 item 带 `id`（首页要靠它匹配 `homeIds`）和 `status`
- `goods.homeIds` 一并导出

### 前端

- `web/goods.html`、`web/index.html` 按 `status` 加 `.is-soldout` class，
  渲染售罄角标与「补货中」提示
- `web-standalone/static-api.js` 的 `mapGood` 补 `id` / `status`，`all` 补 `homeGoods`
- `web/style.css` 里 `.goods-card.is-soldout` 负责降饱和、价格删除线、售罄胶囊

### 降级行为

`homeGoods` 字段**存在但为空**（明确配置为空）→ 首页区块隐藏。
`homeGoods` 字段**缺失**（旧版数据 / 旧接口）→ 退回「前 4 件」，维持老行为。

这样老数据不会因为新功能突然让首页空掉。
