# 版本号规范

> 一句话：**给站点定一个对外版本号 `MAJOR.MINOR.PATCH`，只在「值得对别人说一句『我们更新了』」的时候升；
> 版本号只有一个真源文件，页脚、响应头、提交信息、git tag 全部由脚本派生，不许手抄第二份。**

当前版本：**v1.0.0**（2026-10-19，自持站正式版）

---

## 一、为什么值得做

之前站点没有版本号，问「线上是哪一版」只能靠翻 `git log`。问题有三个：

1. **两条发布通道，同一份内容**：自持动态站直出，GitHub Pages 静态快照另发一次。两边不同步时，没有版本号就无法判断"看到的是哪一版"。
2. **`content.json` 里已经有一个 `version: 5`**。它管的是「前端能不能读懂这份数据」，跟"站点发了第几版"完全是两回事。不给对外版本另起一个名字，早晚有人把它当版本号改，一改就把老页面全挡在门外。
3. **社团对外沟通需要说法**。"这次改了什么"写在提交信息里没人看，写在 CHANGELOG 里、配一个 `v1.0.0`，才是一份能发出去的东西。

---

## 二、两个"版本"必须分清

这是本文最重要的一张表：

| | 站点版本（对外） | 内容结构版本（对内） |
|---|---|---|
| 长相 | `1.0.0` | `5`（单个整数） |
| 存在哪 | `web/version.json` | `data/content.json` 的 `version` 字段 + 页面里的 `MIN_VER` |
| 谁在管 | `scripts/version.mjs` | 人工，改数据结构时同步升 |
| 含义 | 站点第几次对外发布 | 这份数据的字段结构是第几代 |
| 什么时候动 | 发版时 | **只有在增删字段、改字段语义时才动** |
| 动了会怎样 | 页脚数字变 | 老前端会拒绝渲染（`MIN_VER` gate） |

**规则：结构版本不随发版走，站点版本不随结构走。** 一次发版完全可能内容结构版本一点没变（v1.0.0 就是这样，`contentVersion` 仍为 5）。

`version.json` 里两个字段都在，就是为了让脚本能互相校验 —— 页面里的 `MIN_VER` 跟 `contentVersion` 对不上时，`check` 会直接报错。

---

## 三、什么时候升哪一位

| 位 | 什么时候 +1 | 判断标准 | 例子 |
|---|---|---|---|
| **MAJOR** | 不兼容变更 | 老数据/老外链会坏，或有东西被拿掉 | 数据结构大改（结构版本跳代）、URL 结构变、砍掉某个页面、换掉整站技术方案 |
| **MINOR** | 新增对外功能 | 只是"多了"，旧的一切照常 | 新增页面、新增后台能力、新增商品状态、新增区块（本次首页精选 + 售罄/下架就是 MINOR 级） |
| **PATCH** | 修问题 | 行为修正，不新增能力 | 修样式错位、修链接 404、改错别字、换图、价格校准 |

**不升版本的情况**：
- 后台改了几条公告、调了价格、换了一张图 —— **这是内容变动，不是版本**。同步脚本照样会在提交信息里带上当前版本号，但不会替你升位。
- 重构代码但对外行为完全没变 —— 记在提交信息里即可。

一句话判断法：**"这事值不值得在社团群里发一条『官网更新了』？"** 值 → MINOR 起步；只是修修补补 → PATCH；连用户都察觉不到 → 不升。

---

## 四、为什么当前定在 1.0.0

1.0.0 的含义是「第一个可以完整交付、别人能独立用起来的版本」。对着现状逐条核：

| 1.0 应该具备 | 现状 |
|---|---|
| 内容能自己改，不用找人改代码 | ✅ 后台 11 个 tab 全可编辑 |
| 图片能自己传 | ✅ 上传自动转 WebP 并入库 |
| 改完能上线，不用手动敲命令 | ✅ `同步到公网.bat` 一条龙 |
| 数据不会丢 | ✅ `备份.bat` 全量快照 + bundle |
| 不依赖随时会停的第三方 | ✅ Node + `node:sqlite`，零 npm 依赖 |
| 出问题能查 | ✅ 版本号 + CHANGELOG + 备份（本次补齐） |

之前的 0.x 按里程碑倒推记录在 [CHANGELOG.md](CHANGELOG.md) 里：0.1 初版上线 → 0.2 四页成型 → 0.3 内容结构 v5 → 0.4 接自持后端 → 0.5 从能跑到能用 → **1.0 商品三态与首页精选 + 版本体系**。

0.x 那些日期取自 `content.json` 里的公告时间与现场记录，仓库 2026-10-16 才建立，不对应具体提交 —— 这一点 CHANGELOG 里也写明了，不装作有据可查。

## 五、发一次版怎么做

只有四步，全部有脚本兜着：

```bash
cd 官网

# 1) 升版本号（自动改 version.json + 往 CHANGELOG 插占位条目）
node scripts/version.mjs bump minor --name "新增 xx 功能"

# 2) 补两处正文：CHANGELOG 那条占位、version.json 的 summary
#    然后体检（退出码非 0 表示有地方没对齐）
node scripts/version.mjs check

# 3) 提交（提交信息带版本号，方便以后 grep）
git add -A
git commit -m "发布 v1.1.0：新增 xx 功能"

# 4) 打 tag 并推送
node scripts/version.mjs tag --push
```

`bump` 只改 `version` / `released` / `name`（以及给了 `--summary` 时的 `summary`），不会动 `contentVersion` —— 结构版本必须人工确认后单独改，避免脚本猜错。

## 六、版本号会出现在哪六个地方

全部由 `version.json` 派生，**没有第二份真源**：

| # | 位置 | 怎么来的 | 谁看 |
|---|---|---|---|
| 1 | `web/version.json` | **真源，手动改（走 bump）** | 机器 |
| 2 | 四页页脚版权后面的小胶囊 `v1.0.0` | `site.js` 读 `version.json` 渲染 | 访客 / 你自己 |
| 3 | `GET /version.json` | 静态服务直接把真源文件吐出来 | 脚本 / 监控 |
| 4 | 每个响应的 `X-GPIC-Version` 头 | `server/index.mjs` 启动时读一次 | `curl -I` 一眼看线上版本 |
| 5 | 静态快照 `web-standalone/version.json` | `build-standalone.py` 原样复制 | GitHub Pages 那条通道 |
| 6 | 提交信息 `内容同步 v1.0.0：…` | `sync-public.mjs` 读真源拼进去 | 翻 `git log` 时 |

外加第 7 处：**git tag `v1.0.0`**，由 `version.mjs tag` 打，GitHub 上能直接对着 tag 看那一版的文件树。

### 排障用法

```bash
# 线上跑的是哪版？不用登机器
curl -sI https://你的域名/ | grep -i x-gpic-version

# 本地版本有没有走散
node scripts/version.mjs check
```

`check` 会逐项验：真源 JSON 合法、`version` 是 `X.Y.Z`、`released` 是日期、页面的 `MIN_VER` 与 `contentVersion` 同值、四页都有版本占位、`site.js` 有渲染逻辑、`index.mjs` 有响应头、`build-standalone.py` 会复制 `version.json`、CHANGELOG 有对应条目。漏一个就报红。

## 七、两个坑

**坑一：直接改 HTML 里的版本号。**
页脚那个 `v1.0.0` 是 JS 填的，HTML 里只有一个空占位 `<em data-site-version></em>`。看着"没写死"是故意的 —— 写死就等于有了第二份真源。

**坑二：把 `content.json` 的 `version: 5` 改成版本号。**
它必须是整数，且必须与页面里 `var MIN_VER = 5` 相等。改成 `"1.0.0"` 会让所有页面的版本判断直接失效（字符串比较 `"1.0.0" >= 5` 的真实结果取决于实现，别赌）。

---

## 八、一句话交接

**发版只跑 `node scripts/version.mjs bump <位> --name "标题"`，别的什么都别手改。**
`check` 报绿再提交，`tag --push` 收尾。
